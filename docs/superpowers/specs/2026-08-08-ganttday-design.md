# GanttDay 设计文档

- 状态：待用户审阅书面规格
- 日期：2026-08-08
- 工作名：GanttDay（正式名待定，不阻塞开发）

## 1. 产品定位

面向自由职业者与内容创作者的**个人甘特日程工具**。核心价值只有一句：在时间线上看到什么时候做什么。

- **v1 平台：仅 Windows**，以安装包分发（exe / msix）
- **v1 是单人、纯本机应用**，无账号、无网络、无同步
- 需求方日常使用的设备是华为 MatePad（HarmonyOS 6），**平板端明确延后**，但 v1 的代码结构要为那次移植预留（见第 7 节）

### 版本节奏

| 版本 | 范围 |
| --- | --- |
| v1 | 本文档描述的全部内容（Windows） |
| v1.1 | 提醒通知、导出图片 / PDF |
| v2 | 账号、云同步、共享与共同编辑、鸿蒙平板端 |

### v1 明确不做

重复任务、全天任务、提醒通知、任务依赖、里程碑、关键路径、优先级字段、账号、云同步、多人协作、读写系统日历、端到端 UI 自动化测试。

## 2. 平台决策依据

这一节记录为什么 v1 只做 Windows，避免以后重新讨论。

**鸿蒙 6 装不了 APK。** HarmonyOS 6 属于纯血鸿蒙（HarmonyOS NEXT 血统），底层已移除 AOSP 与 ART 运行时，只接受 `.hap` 格式。原本「Flutter 打 APK 装到平板」的路径不成立。

**Flutter 上鸿蒙需要走社区分叉。** OpenHarmony 社区的 Flutter SIG 维护 `flutter_flutter` 分叉，支持 `flutter create --platforms ohos` 与 `flutter build hap`，但版本滞后上游约一个季度。这条路可行，代价是分叉版本会把 Windows 端一起拖到旧版 Flutter，且插件需要逐个确认鸿蒙适配。

**装到自有平板另有门槛。** 需要华为开发者账号并完成实名认证；调试证书绑定设备 UDID，免费账号约 10 台设备，有效期约一年。长期稳定使用的正路是上华为应用市场走审核。

**结论：** v1 只做 Windows，把产品本身验证透；平板端作为后续版本，届时按第 7 节的接口替换实现即可。

## 3. 信息架构与视图

### 任务组织

**扁平任务列表加多标签**，没有项目层级，没有执行人字段。标签既是分类也是过滤维度，其中一个标签被标记为**主标签**，用来决定任务的基础颜色。

### 时间轴方向

**横向时间轴**：时间从左到右，每条任务占一行。这是甘特图的标准形态，也便于 v2 引入依赖箭头。

### 视图层级

- **日视图**：单日，按小时网格排布。v1 首个交付的视图。
- **周视图**：同一条横向时间轴上连续排布 7 天，水平滚动，默认视口约两天宽度，日界线加粗分隔。它与日视图共用同一套绘制，区别仅是可视时间范围这一个参数。
- **月视图**：每天格子内显示最多 3 个任务标题，超出显示 `+N`；点击某天进入该日的日视图。

### 时间精度

- 最小单位为小时，网格按小时绘制
- 拖拽**吸附到 15 分钟**，取舍规则是**四舍五入到最近的 15 分钟**（8:07 归 8:00，8:08 归 8:15）。不用向下取整，因为那会让往右拖时总感觉差一格才跳。
- 任务**最短时长 15 分钟**

### 默认可视时段

默认 8:00–22:00，可在设置中修改。超出该区间的时间通过滚动到达。

### 重叠与跨午夜

- **不同任务时间重叠时各占一行**，纵向排开，不互相遮挡
- **首尾相接不算重叠**：12:00 结束与 12:00 开始的两条任务可以在同一行。理由是连续排期在时间轴上就该看起来连续，若因端点相同而拆行，一个排得紧凑的下午会莫名占掉多行。
- **跨午夜任务在数据库里是一条记录，绘制时切成两段**：23:00–01:00 会在当天画到 24:00、在次日从 00:00 接着画。恰好 00:00 结束的任务不应在次日产生空段。
- 拖动跨午夜任务的任一段等于拖整条，两段联动

## 4. 数据模型

### 时间如何存储

**按本地墙钟存，单位为分钟，不做任何时区换算。** 具体是自 1970-01-01 00:00 起算的分钟数，但该数值直接按本地时间解释。

这样做的理由：若按常规存 UTC 时间戳，系统时区一变（出差、夏令时地区），所有任务在时间轴上会整体平移——写的是 9:00 剪片，到别处打开变成 10:00。对个人日程而言这是错的，9:00 就该永远读作 9:00。分钟精度对 15 分钟吸附完全够用，整数便于排序与范围查询。

代价是该表示不适合跨时区同步。v2 真做同步时需要另加时区字段，属于那时的设计范围，不影响现在。

### 表结构

**任务表 task**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | TEXT | UUID。不用自增整数，因为 v2 要做云同步与共享，自增 ID 会撞车；现在用 UUID 不花额外成本 |
| title | TEXT | 任务名，非空 |
| planned_start | INTEGER | 计划开始（本地墙钟分钟数） |
| planned_end | INTEGER | 计划结束 |
| actual_start | INTEGER? | 实际开始，未完成时为空 |
| actual_end | INTEGER? | 实际结束，未完成时为空 |
| is_done | INTEGER | 0 / 1，仅由手动标记完成置位 |
| primary_tag_id | TEXT? | 主标签，决定基础色 |
| auto_hue | INTEGER | 创建时确定的后备色相，之后不变；无主标签（或主标签被删）时使用 |
| override_hue | INTEGER? | 手动覆盖色相；覆盖只改色相 |
| notes | TEXT? | 备注，用于记录客户要求、素材位置等 |
| created_at | INTEGER | 创建时间 |

**标签表 tag**：`id`（TEXT）、`name`（TEXT，唯一）、`hue`（INTEGER，默认色相）

**关联表 task_tag**：`task_id`、`tag_id`，联合主键。任务与标签是多对多，这样才能一条任务打多个标签并按标签过滤，同时由主标签决定颜色。

**设置表 setting**：键值对。v1 存两项——可视时段起止（默认 8 与 22）、紧迫窗口天数（默认 7）。标签的默认色相存在标签表里，不重复放进设置。

### 索引与范围查询

在 `planned_start` 与 `planned_end` 上建索引。

**查询某日任务不能只看开始时间**，否则跨午夜任务在第二天查不到。正确条件是判断时间段与该日有无重叠：

```
planned_start < 该日 24:00  AND  planned_end > 该日 00:00
```

这样 23:00–01:00 的任务在两天都能被查出，配合切段模块即可在两天的时间轴上各画一截。

### 颜色为什么必须存下来

无标签任务的色相是随机分配的。**若在绘制时才随机，每次打开甚至每次重绘颜色都会变**，甘特图会闪成万花筒。因此色相在创建任务时算一次并写入 `auto_hue`，之后只读。有标签的任务色相直接跟随主标签，无需存储。

## 5. 颜色规则

### 基础色

- 基础色相由**主标签**决定。**同一标签下所有任务的基础色完全一致**，不存在任务级的随机深浅偏移。
- 无标签任务在创建时随机分配一个与已有标签色相距离较远的色相并存下来。
- 手动覆盖色**只定色相**，鲜艳度与置灰仍由紧迫度和完成状态驱动。

之所以不做任务级深浅偏移：颜色的深浅在整个界面上只能有一个含义，就是有多急。若再叠一层随机深浅，用户扫一眼时无法判断眼前这块比旁边深是因为更紧急还是因为随机分到了深色，颜色的信息量就废了一半。

### 未完成任务的紧迫度渐变

只要未完成，就按**距计划结束时间**计算鲜艳度，越接近越艳。这个计算从任务创建起就生效，未到计划开始也会随时间推进渐渐变艳。

- **紧迫窗口默认 7 天，可在设置中修改。** 距计划结束超过窗口时一律显示最淡色。
- **渐变曲线为线性**：颜色深浅直接对应剩余时间占窗口的比例。

### 逾期未完成

越过计划结束时间但未标记完成时：

- 鲜艳度**封顶不再变化**
- 叠加**斜纹填充与描边**作为逾期标记
- **条形停留在原计划位置，不向当前时间拉长**

不拉长的理由有两条：拉长会让逾期任务不断变宽并与后续任务重叠成一片；而且「条形长度反映真实占用」这套视觉语言属于完成后的实际条，不该被逾期状态提前占用。用纹理而非换色来表达逾期，则保留了标签色相，用户仍能分辨逾期的是哪一类活。

### 已完成任务

计划与实际**叠合在同一行内**：

- **计划条**在下层，较粗，在原色基础上置灰，位置停在原计划时间
- **实际条**在上层，较细，居中压在计划条上，使用鲜艳色
- 实际条**从头到尾单一颜色**，不对超出计划的部分做分段高亮
- 三种情形均支持：实际比计划长时实际条两端伸出灰条；实际比计划短时缩在灰条内、两侧露出灰底；实际与计划完全错开时两条不相交但仍在同一行

计划与实际的偏差靠两条的错位来读：左端比灰条突出多少就是提前多久，右端超出多少就是超时多久。

### 绘制层的辨识度处理

由于同标签任务基础色一致，紧迫度接近的两条任务颜色会几乎相同。绘制时给每个条形留固定间隙并加一圈比自身略深的描边。这纯属绘制层职责，不影响上述配色规则。

## 6. 交互流程

### 创建

两条路径并存：点「新建」进入表单页；在日 / 周视图空白处拖拽画出时间块，松手后填标题。

### 编辑

- 拖条身：整体平移，时长不变
- 拖条两端：改时长。越过对面端点时停在最短时长，不产生负时长——由几何模块的吸附函数从源头保证，非法值进不到数据层
- 已完成任务在主视图**不可拖动**。因为它此刻承载着计划与实际的对照，若能随手拖动计划条，用户将无法分辨眼前的灰条是原始计划还是事后挪动过的。要修改需先撤销完成，或在完成弹窗内调整实际时间。

### 标记完成

**仅手动标记**，不因越过计划结束时间而自动完成——自动完成会误伤「拖期但仍在做」的任务。

点击完成后弹出时间编辑弹窗：

- 弹窗内有一条时间轴标尺
- **计划参考条**置灰、缩小弱化、位置严格锁定在原计划起止，不可拖拽，仅作对照标尺
- **选区框**是弹窗内唯一可操作的组件，左右两端各有拖拽手柄，用于调整实际开始与实际结束
- 选区不受计划条边界约束，可向左超出（提前开工）也可向右超出（超时收尾）。超出计划的部分在**弹窗内**用高饱和色高亮并附箭头提示
- 允许选区完全包裹计划区间、部分重叠、或与计划完全错开
- 打开时选区默认等于计划区间，不想细究可直接确认

**时间轴的缩放行为：**

- 初始范围为计划区间前后各 1 小时，选区等于计划区间
- 正常拖动范围内**时间轴不动**
- 当选区将要越过弹窗可视边界时，时间轴**缩小刻度并整体平移视口**，保证完整选区始终可见。向右拖出界则轴缩小、视口左移；向左拖出界则轴缩小、视口右移
- **拖动过程中只缩不放**；松手后按最终选区重算一次最合适的刻度，平滑过渡到位。不做双向实时跟随，因为往回收时刻度一放大，手指下的时间点会朝反方向跑，用户得追着它调，这是拖拽交互里最难受的一种反馈
- **缩放下限**：15 分钟对应像素不低于约 8px。触底后不再继续缩小，改为允许选区超出视口，此时靠数字读时间
- 拖动过程中**实时显示精确起止时间文字**，使精度不再完全依赖眼睛对齐像素

确认后弹窗关闭，主甘特图按第 5 节的规则渲染灰计划条与鲜艳实际条。

### 撤销与修改

可事后重新打开弹窗修改实际时间；也可撤销完成，回到未完成状态并**清除实际时间**（不留脏数据）。

## 7. 架构

采用**适度预留**策略：只守两条纪律，为将来的鸿蒙移植省下大部分工作，而现在只多付约一成成本。

### 分层

**领域层（纯 Dart，零平台依赖、零 Flutter 依赖）**

这是项目最值钱的部分，移植时原样搬走。四个模块：

| 模块 | 职责 |
| --- | --- |
| `GanttGeometry` | 时间与像素互换：`时间 → X 坐标`、`X 坐标 → 时间`、15 分钟吸附。输入输出皆为数值 |
| `DaySegmenter` | 跨午夜切段：给定一条任务与一个日期，输出该任务落在该日内的时间段 |
| `LaneLayout` | 重叠分行：输入当日所有时间段，输出每段占第几行 |
| `UrgencyPalette` | 颜色与紧迫度：输入基础色相、计划起止、当前时间、完成状态、实际起止、紧迫窗口天数，输出计划条颜色、实际条颜色、是否绘制逾期斜纹 |

这四件事是本应用全部的逻辑难点。做成纯函数后，不启动界面、不连数据库即可为每条规则写死用例。

**平台层（移植时唯一需要重写的部分）**

上层代码只依赖这三个接口的方法签名：

| 接口 | 职责 | v1 实现 |
| --- | --- | --- |
| `TaskRepository` | 按日期范围查询、增删改、标记完成 / 撤销完成，变更以数据流推给界面 | 本地 SQLite |
| `SettingsStore` | 可视时段、紧迫窗口天数、标签及默认色 | 本地 SQLite |
| `FileGateway` | 选文件、读文本、写文本 | Windows 文件对话框 |

**界面层（Flutter，跨平台，移植时基本不动）**

日视图甘特（画布加手势）、任务表单页、完成弹层、设置页。

界面层不包含任何时间换算或颜色计算，只调用领域层与平台接口。甘特画布只接收「已算好行号与颜色的时间段列表」并绘制，因此改配色规则或分行策略时不会牵动绘制代码。

### 这样分层的收益

1. 最容易写错的地方最容易测
2. 绘制代码与数据来源解耦
3. 换平台的改动是可数清的：三个接口、三个新实现

## 8. 错误处理

**数据库打不开时绝不静默重建空库。** 文件损坏或被其他进程占用时，明确告知无法打开及原因，并提供「将损坏文件另存到旁边，再新建空库继续使用」的选择。静默重建是最坏的做法：用户打开应用发现所有任务消失，还不知道原文件是否有救。

**写入失败时不假装成功。** 磁盘满或权限不足时，界面回滚到操作前状态并提示失败。这在拖拽场景下尤为重要——若拖完显示成功但实际未落盘，用户下次打开会看到它弹回原位，而那时已不记得原来是几点。

**导入备份走整体校验加事务。** 先校验版本号、必填字段与时间合法性，全部通过才写入；任何一条不合格则整体拒绝，并列出问题出在哪几条。不做部分导入，因为半截数据比导入失败难收拾得多。遇到 id 已存在的任务默认**跳过并汇报跳过数量**，不覆盖——覆盖不可逆，跳过之后用户仍可决定如何处理。

**表单校验就地拦截。** 结束时间早于开始时间时不允许保存。

## 9. 备份文件格式

JSON，包含版本号、导出时间、全部任务、全部标签、全部设置。用于防止数据丢失，不构成多端同步。

## 10. 测试策略

**领域层单元测试是重点。** 关键用例：

- 吸附的四舍五入边界
- 跨午夜切段：23:00–01:00 在两天各产生一段；恰好 00:00 结束的任务不在次日产生空段
- 分行算法：完全重叠、部分重叠、首尾相接三种情形
- 颜色规则：窗口外恒定最淡、逾期封顶不再变化、完成后置灰

**存储层用内存数据库测试**，重点两项：按日期范围查询必须能查到跨午夜任务（最易写错的 SQL 条件）；完成与撤销完成时字段变化干净，撤销必须真正清除实际时间。

**界面层只写少量测试**，覆盖两条核心路径：拖拽建块产生的时间正确；完成弹窗返回的实际时间正确。

**不做端到端 UI 自动化**：单人项目里维护成本高、发现问题少，同样的工夫花在领域层用例上回报大得多。

## 11. 开发顺序

1. 本地任务 CRUD 加日视图甘特（含拖拽建块、拖动改期、拖两端改时长、今天线）
2. 完成弹层与撤销完成
3. 标签与按标签过滤
4. 周视图与月视图
5. 设置页（可视时段、紧迫窗口）
6. 备份导入导出

先做第 1 步的理由是尽早在真实窗口里拖动任务，验证小时级甘特的手感是否合格——这是整个产品成立与否的前提。
